Manual de Arquitectura y Especificación Técnica

Documentación técnica profunda para desarrolladores, auditores y administradores de infraestructura sobre el diseño de software, esquemas de bases de datos, seguridad criptográfica y endpoints de la plataforma Congreso ETS 2026.

Arquitectura Monorepo Desacoplado PostgreSQL 16 Normalizado 3FN Cifrado AES-256-CBC Next.js 14 + Node.js Express

1. Arquitectura General del Sistema

La plataforma está diseñada siguiendo una arquitectura modular desacoplada cliente-servidor (Frontend SPA/SSR + Backend RESTful API) con persistencia relacional en PostgreSQL y capacidad de ejecución en modo desconectado mediante Service Workers y base de datos local IndexedDB.

3. Modelo Relacional Normalizado en Tercera Forma Normal (3FN)

El esquema de base de datos reside en backend/database/schema_3fn.sql. Se diseñó bajo las reglas estrictas de la Tercera Forma Normal para erradicar redundancias, anomalías de inserción, actualización y borrado.

3.1 Entidades Principales

  • usuarios: Asistentes e inscriptos con datos identificatorios y token de credencial.
  • operadores: Personal con acceso al sistema administrativo o estaciones de escaneo.
  • roles: Jerarquías y niveles de privilegio (Superadmin: 5, Administrador: 4, Verificador: 3, Operador: 2, Asistente: 1).
  • actividades: Conferencias, paneles y talleres con fecha, hora inicio/fin y aforo.
  • salas: Espacios físicos de la sede con capacidad máxima reglamentaria.
  • inscripciones_actividades: Relación N:M entre asistentes y actividades con estado (INSCRIPTO, LISTA_ESPERA, CANCELADO).
  • puntos_acceso: Terminales o puertas de ingreso físico habilitadas.
  • acreditaciones: Registros inmutables de check-in con marca temporal y operador responsable.
  • certificados: Registro de diplomas generados con hash de validación criptográfica.
  • encuestas: Definición de encuestas de satisfacción, ventanas de vigencia y bloqueo de certificados.
  • encuesta_preguntas: Batería de preguntas normalizadas (estrellas, texto, opciones) vinculadas a cada encuesta.
  • encuesta_respuestas: Respuestas registradas por los participantes con control de unicidad.
  • configuraciones_sistema: Almacén de pares clave-valor (SMTP, push, sandbox, cupos, plantilla_certificado_oficial).
  • auditoria_logs: Trazabilidad forense inmutable de todas las mutaciones del sistema.
Diccionario de Datos Completo: Consulte el Diccionario de Datos Normalizado (3FN) para ver el catálogo exhaustivo de los 21 modelos de datos, atributos, claves primarias, foráneas, valores por defecto y propósitos de negocio clasificados por módulos.

3.2 Disparadores (Triggers) de Integridad y Trazabilidad

-- Trigger de actualización automática de marca temporal
CREATE OR REPLACE FUNCTION actualizar_timestamp()
RETURNS TRIGGER AS $$
BEGIN
    NEW.actualizado_en = CURRENT_TIMESTAMP;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

-- Trigger de Registro Forense Inmutable
CREATE OR REPLACE FUNCTION auditar_cambios()
RETURNS TRIGGER AS $$
BEGIN
    INSERT INTO auditoria_logs (tabla_afectada, operacion, registro_id, datos_previos, datos_nuevos)
    VALUES (TG_TABLE_NAME, TG_OP, COALESCE(NEW.id, OLD.id), row_to_json(OLD), row_to_json(NEW));
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

4. Motor Criptográfico y Seguridad de Códigos QR

Implementado en backend/src/lib/cryptoQR.ts. Para impedir la falsificación de gafetes o la alteración manual del DNI en el código óptico, se utiliza el algoritmo de cifrado simétrico AES-256-CBC con Vector de Inicialización (IV) dinámico de 16 bytes.

4.1 Estructura del Payload Cifrado

{
  "u": 1042,                        // ID único de usuario en base de datos
  "d": "35890123",                  // DNI o Pasaporte del asistente
  "r": 1,                           // Rol asignado
  "t": 1790400000000,               // Timestamp de emisión (milisegundos)
  "h": "a1b2c3d4e5f6..."            // HMAC-SHA256 para integridad
}

4.2 Formato del Código QR en el Gafete

El código generado y almacenado en el QR tiene el formato:

[IV_HEX_32_CHARS]:[CIPHERTEXT_HEX]
Ejemplo: 4f8a1c9e2b3d...:8d9e2a1b5c6f7a8b9c0d...
Ventaja de Seguridad: Aun si un atacante conoce el DNI de otra persona, no puede fabricar un código QR válido porque desconoce la clave simétrica ENCRYPTION_KEY de 32 bytes custodiada exclusivamente en el servidor.

5. Seguridad, Autenticación y Autorización

  • Almacenamiento de Contraseñas: Las contraseñas de los operadores se procesan mediante crypto.pbkdf2Sync con sal (salt) aleatorio de 16 bytes, 100.000 iteraciones de SHA-512, almacenándose como [salt_hex]:[hash_hex].
  • Transporte de Sesión: Se emite un JSON Web Token (JWT) firmado con algoritmo HS256 transmitido en una cookie HTTP-Only con directivas SameSite=Lax y expiración de 7 días.
  • Control de Acceso Basado en Roles (RBAC): El middleware requerirJerarquia(nivelMinimo) intercepta cada petición a la API y valida que operador.jerarquia >= nivelMinimo.

6. Motores de Negocio Centrales

6.1 Motor de Conflicto y Solapamiento de Horarios (ConflictEngine)

Ubicado en backend/src/lib/conflictEngine.ts. Antes de asentar una inscripción a un taller, calcula la intersección temporal:

-- Condición de Solapamiento Temporal:
(nueva.inicio < existente.fin) AND (nueva.fin > existente.inicio)

Si la condición se cumple, la API devuelve error ERR_HORARIO_SOLAPADO con el nombre de la actividad en conflicto.

6.2 Motor de Lista de Espera y Promoción Automática

Cuando un asistente cancela su inscripción o un administrador amplía el cupo, se ejecuta una transacción atómica FIFO (First In, First Out):

  1. Selecciona el primer registro con estado LISTA_ESPERA ordenado por creado_en ASC.
  2. Actualiza el estado a INSCRIPTO.
  3. Despacha un correo electrónico y notificación push al participante notificando su pase a cupo titular.

6.3 Motor Dinámico de Certificados Vectoriales (PDF-Lib)

Implementado en backend/src/lib/certificatePdfService.ts y consumido por las rutas de backend/src/routes/admin/certificados.routes.ts. El sistema desacopla los textos, colores y autoridades firmantes del código fuente duro, cargándolos en tiempo de ejecución desde la clave plantilla_certificado_oficial de la tabla configuraciones_sistema.

  • Renderizado Vectorial en Milisegundos: Genera documentos PDF apaisados A4 (841.89 x 595.28 pt) con doble orla geométrica perimetral, paleta tipográfica dinámica (encabezado, títulos, cuerpo, firmas) y cálculo automático de centrado horizontal por métricas de glifos StandardFonts.Helvetica.
  • Cálculo Automático de Firmantes y Sellos: Distribuye equitativamente en el eje X de 1 a 4 autoridades firmantes calculando márgenes y líneas de rúbrica vectoriales de manera responsiva.
  • Validación Forense Criptográfica: Incrusta código QR con URL canónica absoluta (/certificados/validar/:hash) y el hash SHA-256 único de validación para prevenir falsificaciones en papel o formato digital.
  • Vista Previa WYSIWYG y Descarga de Prueba: El endpoint POST /api/admin/certificados/plantilla/preview recibe el payload JSON del diseñador y devuelve un buffer binario application/pdf en tiempo real con datos de un participante ficticio sin necesidad de persistir cambios preliminares en la base de datos.

6.4 Motor de Encuestas de Calidad y Bloqueo Pedagógico

Ubicado en backend/src/routes/encuestas.routes.ts y backend/src/routes/certificados.routes.ts. Regula la recolección de métricas de satisfacción y el condicionamiento obligatorio de emisión de credenciales finales:

  • Diseñador y Transacción Atómica de Sincronización (WYSIWYG Sync): El endpoint PUT /api/encuestas/:id/sync-completa procesa en un único bloque transaccional ACID (BEGIN...COMMIT) los metadatos de la encuesta (título, descripción, vigencia, obligatoriedad) y la recreación ordenada de su batería de preguntas (estrellas 1-5, opciones radio, respuesta libre).
  • Bloqueo Pedagógico de Descarga: Si una encuesta activa posee la directiva obligatoria_para_certificado = true, el motor de certificados rechaza la descarga o emisión de diplomas (403 Forbidden - ENCUESTA_PENDIENTE) hasta que el asistente complete la encuesta desde su portal personal.
  • Métricas de Satisfacción Agregadas: Consolida respuestas en tiempo real computando promedios de calificación por estrellas, distribución porcentual de opciones múltiples y libro abierto de devoluciones cualitativas.

8. Motor PWA Offline y Sincronización

Implementado mediante el Service Worker frontend/public/sw.js y el hook reactivo useOfflineAcreditacion.ts.

8.1 Estrategia de Caché

  • App Shell (HTML/CSS/JS): Estrategia Cache First con actualización en segundo plano (Stale-While-Revalidate).
  • Consultas API de Validación: Estrategia Network First con persistencia en IndexedDB como almacén de contingencia.

8.2 Esquema del Almacén Local IndexedDB (congreso_offline_db)

Almacén: 'asistentes_cache'  -> KeyPath: 'dni'  (Índice por 'token_qr')
Almacén: 'cola_sincronizacion' -> KeyPath: 'id_transaccion' (Autoincremental)
  {
    "id_transaccion": 101,
    "dni": "35890123",
    "punto_acceso_id": 1,
    "timestamp": 1790412345000,
    "operador_id": 4,
    "sincronizado": false
  }

8.3 Subsistema Web Push VAPID PWA y Segmentación de Audiencias

El portal integra notificaciones push estándares W3C/IETF con cifrado RFC 8292 (VAPID) estructurado con reglas estrictas de destinatarios:

  • Generación de Par de Claves: Claves VAPID administradas en backend con web-push y expuestas vía GET /api/push/public-key.
  • Suscripción desde Cliente: Gestionada por el componente PushNotificationToggle.tsx y el Service Worker (sw.js), con fallback amigable cuando los permisos son denegados o el navegador no soporta PushManager.
  • Emparejamiento de Suscripción con Usuario Registrado: Al suscribirse (POST /api/push/subscribe), el endpoint extrae el usuario_id de la sesión autenticada o token del participante y lo almacena en suscripciones_push.
  • Notificación Unidireccional de Bienvenida: Se despacha exclusivamente al endpoint del navegador que solicitó el alta, sin afectar a otros usuarios.
  • Notificaciones Individuales de Transición: El motor de cupos y confirmaciones (sendPushNotificationToUser) notifica únicamente al usuario individual promovido desde lista de espera o al recibir asignaciones personales.
  • Segmentación de Difusión Masiva (Broadcast): La función broadcastPushNotification(payload, filter) aplica filtros SQL estrictos:
    • sp.usuario_id IS NOT NULL: Excluye de forma categórica a visitantes anónimos o suscripciones desvinculadas.
    • filter.rol_id: Filtra por categoría institucional (e.g. únicamente Estudiantes o Docentes).
    • filter.solo_acreditados = true: Realiza un INNER JOIN acreditaciones a ON a.usuario_id = sp.usuario_id AND a.tipo_movimiento = 'INGRESO', limitando el envío únicamente a los asistentes que ya pasaron por el escáner de acceso físico en la sede.

8.4 Motor Dinámico de Actividades y Cronograma

La vista pública del cronograma (/programa y componente ProgramaCongreso.tsx) realiza llamadas en tiempo de ejecución a GET /api/actividades con revalidación periódica. Cualquier cambio, reprogramación de orador o actualización de aforo efectuada en el panel administrativo impacta de manera inmediata en la grilla visual de los asistentes.

11. Arquitectura de Despliegue Nativo en Windows 10 y 11

A diferencia del entorno de desarrollo que utiliza contenedores, la versión desplegada en Windows corre de manera 100% Nativa:

  • Base de Datos: Servicio estándar de Windows postgresql-x64-16 gestionado mediante el Administrador de Servicios (services.msc).
  • Backend: Proceso de Node.js en puerto 4000 iniciado en segundo plano sin terminal bloqueante.
  • Frontend: Servidor de producción en puerto 3000 con soporte de renderizado Next.js.
  • Control del Sistema: Orquestado mediante scripts por lotes (Iniciar_Congreso.bat y Detener_Congreso.bat) sin requerir Docker, WSL2 ni virtualización.

12.2 Aislamiento Estricto mediante `.admin-root`

En frontend/app/globals.css, todas las reglas de reasignación visual están encapsuladas bajo el selector descendente .admin-root. Esto garantiza que las rutas públicas (/, /participa, /mi-credencial) y las plantillas de impresión oficial de gafetes A4 no reciban ninguna interferencia de estilo:

.admin-root {
  background-color: var(--admin-bg, #f8fafc) !important;

12.3 Reactividad en Caliente y Event Bus

Cuando el operador interactúa con el componente AdminThemeEditor.tsx o AdminFrontendThemeEditor.tsx:

  1. Los valores modificados se persisten inmediatamente en localStorage (claves congreso_backend_theme / congreso_frontend_theme y sus variantes personalizadas).
  2. Se despachan eventos nativos desacoplados: backend-theme-changed para el panel o frontend-theme-changed para el portal público.
  3. El contenedor raíz del panel (admin/page.tsx) o el proveedor de portal (FrontendThemeProvider.tsx) escuchan el evento y actualizan en caliente las variables CSS inyectadas en tiempo real sin recargar la página.

12.4 Persistencia Centralizada en PostgreSQL (Default Global)

Para garantizar uniformidad institucional sin configurar manualmente cada equipo:

  • Tabla configuraciones_sistema: Almacena el objeto JSON bajo las claves:
    • 'tema_backend_default': Configuración visual del panel administrativo para los operadores.
    • 'tema_frontend_default': Configuración visual predeterminada del portal público para todos los visitantes y participantes.
    {
  "themeId": "caba-oficial",
  "themeName": "Paleta Oficial CABA Institucional",
  "customVars": null,
  "actualizado_en": "2026-09-26T01:30:00.000Z"
}
  • Seguridad & Auditoría: Los endpoints PUT /api/admin/configuracion/tema-default y PUT /api/admin/configuracion/tema-frontend-default exigen jerarquía mínima 4 (Administrador) y registran automáticamente el cambio en logs_auditoria (módulo CONFIGURACION, acción TEMA_DEFAULT_UPDATE o TEMA_FRONTEND_DEFAULT_UPDATE) con el ID del operador responsable.
  • Secuencia de Carga y Fallbacks: Tanto en el backend como en el frontend público, los componentes verifican primero las preferencias locales en localStorage. Si no existen, consultan los endpoints correspondientes de configuración global en PostgreSQL y realizan la hidratación automática de las variables de diseño.
