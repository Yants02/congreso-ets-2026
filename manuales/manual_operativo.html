Manual de Operación, Mantenimiento y Administración IT

Guía de referencia técnica y operativa para administradores de sistemas, personal de soporte IT y coordinadores de acreditación del Congreso ETS 2026.

Despliegue Nativo Windows 10/11 PostgreSQL Service Manager SMTP Google App Passwords Protocolo de Contingencia Offline

1. Requisitos de Infraestructura y Servidor

Parámetro Requisito Mínimo Recomendado para Producción
Sistema Operativo Microsoft Windows 10 (64-bit) Windows 10 / 11 Pro o Windows Server 2022
Procesador Intel Core i3 / AMD Ryzen 3 (4 núcleos) Intel Core i5 / AMD Ryzen 5 o superior
Memoria RAM 4 GB 8 GB a 16 GB
Almacenamiento 5 GB libres en disco SSD 20 GB libres en disco NVMe SSD
Motor de Base de Datos PostgreSQL 14 Nativo para Windows PostgreSQL 16 (Servicio Windows estándar)
Runtime de Aplicación Node.js 18.18.0 LTS Node.js 20.x o 22.x LTS
Sin Docker en el Equipo Destino: El sistema corre de forma nativa sobre el sistema operativo Windows utilizando el servicio oficial de PostgreSQL y los binarios de Node.js, optimizando el consumo de memoria a menos de 300 MB totales.

2. Instalación y Despliegue en Windows y Linux

El despliegue se realiza mediante los paquetes autónomos distribuibles:

2.1 Despliegue en Microsoft Windows 10 y 11

Utilizando el paquete CongresoETS2026_Instalador_Windows.zip:

  1. Descompresión: Extraer el archivo ZIP en cualquier ubicación temporal (ej: el escritorio o unidad externa).
  2. Ejecución del Lanzador: Hacer clic derecho sobre Instalar_CongresoETS2026.bat y seleccionar "Ejecutar como Administrador".
  3. Auditoría Previa: El instalador revisará la presencia de Node.js, NPM y PostgreSQL. Si algún componente está ausente, presentará opciones directas para abrir los instaladores oficiales.
  4. Directorio Destino: Elegir la carpeta definitiva (por defecto: C:\CongresoETS2026).
  5. Aprovisionamiento de Base de Datos: El asistente creará automáticamente la base de datos congreso_ets2026 y ejecutará schema_3fn.sql y seed.sql.
  6. Generación de Claves Criptográficas: Se generará una clave aleatoria de 32 bytes (AES-256) en backend/.env.
  7. Compilación y Accesos Directos: Se instalarán los paquetes de Node y se creará el acceso directo en el Escritorio.

2.2 Despliegue en Distribuciones Linux (Ubuntu, Debian, Mint, Fedora)

Utilizando el paquete CongresoETS2026_Instalador_Linux.tar.gz:

  1. Descompresión: Extraer el archivo comprimido mediante el comando: 
    tar -xzf CongresoETS2026_Instalador_Linux.tar.gz
cd CongresoETS2026_Instalador_Linux
  2. Ejecución del Asistente: Lanzar el script instalador interactivo: 
    ./instalar.sh
  3. Auditoría y Parámetros: El asistente verificará la versión de Node.js, NPM y el daemon de PostgreSQL, solicitará la carpeta destino (por defecto: ~/CongresoETS2026) e inicializará el esquema 3FN y las claves criptográficas.
  4. Arranque del Sistema: Para iniciar el congreso en cualquier momento, basta con ejecutar ./Iniciar_Congreso.sh o hacer doble clic en el acceso directo de escritorio generado (Congreso_ETS_2026.desktop).

3. Operación y Ciclo de Vida del Servicio

3.1 Rutina de Inicio del Sistema

Para encender la plataforma al inicio de la jornada:

# Desde la carpeta de instalación (C:\CongresoETS2026) o acceso directo:
Iniciar_Congreso.bat

El script:

  • Levanta el Backend API en http://localhost:4000.
  • Levanta el Frontend Web en http://localhost:3000.
  • Espera la respuesta del servidor y abre automáticamente el navegador en http://localhost:3000.

3.2 Rutina de Detención Limpia

Para apagar los servicios de forma ordenada sin dejar procesos huérfanos:

# Ejecutar:
Detener_Congreso.bat

El script detecta los identificadores de proceso (PIDs) que ocupan los puertos 3000 y 4000 y envía una señal de terminación limpia.

3.3 Comprobación de Estado (Health Check)

# Comprobar estado de la API:
curl -s http://localhost:4000/api/configuraciones

4. Administración de Base de Datos PostgreSQL

PostgreSQL se ejecuta como un Servicio de Windows denominado postgresql-x64-16.

4.1 Control del Servicio desde Consola Administrativa (PowerShell)

# Iniciar el servicio:
Start-Service -Name postgresql*

# Detener el servicio:
Stop-Service -Name postgresql*

# Comprobar estado:
Get-Service -Name postgresql*

4.2 Conexión Manual por Consola (psql)

psql -h localhost -p 5432 -U postgres -d congreso_ets2026

5. Política de Backups y Recuperación de Desastres (DR)

El sistema cuenta con un motor de respaldo con separación estricta de responsabilidades entre la estructura (DDL) y los datos transaccionales.

5.1 Generación de Backups desde el Panel de Control

Desde /admin?tab=auditoria, el Superadmin puede generar y descargar copias de seguridad en formato ZIP:

  • backup_completo_[fecha].zip: Incluye DDL de tablas y volcado completo de datos.
  • backup_datos_[fecha].sql: Solo sentencias INSERT de datos de participantes y acreditaciones.

5.2 Procedimiento de Restauración Manual de Emergencia

# 1. Detener el sistema con Detener_Congreso.bat
# 2. Restaurar el esquema y datos utilizando psql:
set PGPASSWORD=tu_password_postgres
psql -h localhost -p 5432 -U postgres -d congreso_ets2026 -f C:\Ruta\schema_3fn.sql
psql -h localhost -p 5432 -U postgres -d congreso_ets2026 -f C:\Ruta\volcado_datos.sql

6. Configuración de Correo SMTP Google y Notificaciones

Google exige el uso obligatorio de Contraseñas de Aplicación de 16 caracteres para clientes de correo de terceros sin OAuth2.

Requisito Google: No utilice la contraseña personal habitual de Gmail. Debe generar un token de aplicación desde la consola de seguridad de Google.
  1. Acceder a la cuenta institucional en: https://myaccount.google.com/security
  2. Verificar que la "Verificación en dos pasos" esté activada.
  3. Ingresar a Contraseñas de aplicaciones (https://myaccount.google.com/apppasswords).
  4. Crear una nueva contraseña asignando el nombre "Congreso ETS 2026".
  5. Copiar el código de 16 letras generado (ej: xxxx yyyy zzzz wwww).
  6. Ingresar al panel administrativo en /admin?tab=configuracion, pegar el código en el campo de contraseña y pulsar "Probar Conexión".

Uso del Modo Sandbox Institucional:

Durante los ensayos previos al evento, se recomienda activar el interruptor "Modo Sandbox Institucional". En este modo, todas las inscripciones y acreditaciones generan los gafetes y QRs normalmente, pero los correos se simulan registrándose en los logs sin enviar correos reales al exterior.

7. Protocolos Operativos Durante el Evento

7.1 Puntos de Entrada y Check-in Rápido

  • Cada operador se posiciona en una terminal o dispositivo móvil con acceso a /pwa-operador.
  • El asistente presenta su código QR desde la pantalla de su celular o en gafete impreso.
  • El escáner confirma el ingreso con una señal visual verde y un pitido audible en menos de 0.3 segundos.
  • Si el asistente no posee su código QR, el operador realiza la búsqueda por DNI en el padrón y pulsa "Acreditar Manualmente".

7.2 Prevención de Doble Ingreso:

Si una misma credencial se escanea por segunda vez, el sistema emite una alerta roja indicando "ASISTENTE YA ACREDITADO HOY A LAS XX:XX HS" con el nombre de la puerta anterior.

7.3 Procedimiento de Configuración de Diplomas y Encuestas Post-Evento

Previo a la ceremonia de clausura y apertura de descarga de certificados, el Administrador o Director debe ejecutar las siguientes verificaciones operativas:

  1. Revisión de Firmantes Oficiales (WYSIWYG Diplomas): Ingresar a /admin?tab=certificados y pulsar "🎨 Diseñar Plantilla de Certificado". Validar que las autoridades firmantes (Nombre, Cargo y Orden) coincidan con la comitiva que presidirá la entrega oficial.
  2. Auditoría de Descarga de Prueba: Pulsar "Descargar PDF de Prueba" para inspeccionar visualmente que no existan desbordes tipográficos ni solapamientos en las líneas de rúbrica vectoriales.
  3. Activación de la Encuesta de Satisfacción con Bloqueo Pedagógico: Ingresar a /admin?tab=encuestas, verificar que la encuesta del congreso tenga la casilla "Obligatoria para descargar certificado" activada y el rango de fechas en curso.
  4. Monitoreo de Devoluciones: Consultar el panel de "Métricas y Satisfacción" periódicamente para observar el índice de respuesta y calificaciones de los talleres en vivo.

7.4 Criterios Operativos de Admisión y Estados por Rol

Al gestionar el padrón de participantes en /admin?tab=usuarios o /admin?tab=acreditaciones, los coordinadores deben respetar las siguientes directrices:

  • Participantes con Rol "Estudiante": Son los únicos sujetos a las reglas de "Lista de espera", "Baja Automática 48hs" (por falta de confirmación tras notificación de cupo) y "Sancionados" (por inasistencia injustificada reiterada según normativa).
  • Docentes, Autoridades, Invitados Especiales y Prensa: Su estado solo transita entre Confirmado y Cancelado. La interfaz bloquea automáticamente cualquier intento accidental de asignar estados disciplinarios o de lista de espera a estos roles.

7.5 Difusión de Avisos por Notificaciones Push PWA y Segmentación de Destinatarios

Para emitir avisos urgentes (cambio de sala de un panel, inicio de receso o recordatorio de encuestas) desde el panel de control (/admin?tab=push):

  • Requisito de Suscripción Previa: Los destinatarios deben haber pulsado "Activar Notificaciones" desde el portal público estando registrados con su cuenta.
  • Garantía Anti-Spam a Visitantes Anónimos: El sistema nunca envía avisos masivos a usuarios sin registrar o anónimos; cada notificación está anclada a una cuenta del padrón oficial.
  • Segmentación Operativa por Audiencia:
    • Todos los Inscriptos: Difunde la novedad a todo el padrón de participantes registrados que tengan su dispositivo suscrito. Ideal para avisos generales de apertura o cierre.
    • Por Rol Institucional (Estudiantes, Docentes, Disertantes): Segmenta el mensaje únicamente para el grupo seleccionado (ej. aviso de reunión exclusiva de disertantes o indicaciones para docentes).
    • Solo Acreditados Presentes en Sala: Filtro de alta precisión que entrega la notificación únicamente a los participantes que ya ingresaron físicamente a la sede (registrados por el escáner de acreditación QR). Permite avisar cambios de sala o pausas de café sin importunar a quienes siguen en su domicilio o viaje.
  • Notificaciones Automáticas Individuales: El sistema emite de forma automática avisos push privados y exclusivos al participante correspondiente cuando es promovido de Lista de espera a Confirmado por liberación de cupo.

7.6 Personalización Visual: Temas del Backend y Temas del Frontend

Desde la pestaña /admin?tab=configuracion, los administradores disponen de dos módulos de tematización visual independiente:

  • 🎨 Temas del Backend: Permite personalizar la apariencia de todo el panel administrativo de control (fondos, tarjetas de datos, inputs, tablas y botones de acción).
  • 🌐 Temas del Frontend: Brinda un inspector interactivo en tiempo real para modificar la estética del portal público visible por los participantes (Hero principal, Barra de navegación, Tarjetas de conferencias, Botón de Inscripción y Footer).
  • Fijar como Default Global: Al pulsar "💾 Fijar como Default Global" en cualquiera de los dos módulos, la configuración seleccionada se almacena en PostgreSQL y se aplica automáticamente a todos los nuevos visitantes u operadores del sistema.
  • Exportación e Importación: Se pueden exportar las paletas en formato JSON para transferirlas entre entornos de desarrollo, pruebas y producción sin fricción.

8. Protocolo de Contingencia sin Conexión y Modalidades de Operación

Si la red de la sede colapsa o sufre micro-cortes:

  1. Detección Automática: La PWA detecta el evento window.onoffline y conmuta de inmediato a modo desconectado.
  2. Validación Local: El escáner valida la autenticidad del código QR descifrando el payload criptográfico y contrastándolo con la copia local en IndexedDB.
  3. Registro en Cola: Cada check-in se guarda en la cola local queue_acreditaciones con marca de tiempo precisa.
  4. Reconexión y Sincronización: En cuanto el dispositivo vuelve a tener señal Wi-Fi o datos móviles, la cola se despacha automáticamente al endpoint /api/operator/acreditar-batch sin duplicar registros.
  5. Panel de Monitoreo Offline: Tanto en la terminal de acreditación como en la barra superior del panel administrativo se dispone del botón "Gestor Cola" / "Sync OK". Este modal permite ver en detalle los tokens retenidos localmente, forzar la subida manual o purgar la cola si fuera necesario.

8.1 Modo Kiosco para Terminales Fijas y Tótems de Acreditación

En puestos de alta demanda o tótems equipados con pistolas lectoras de códigos de barras/QR USB o Bluetooth:

  • Activación Pantalla Completa: Al presionar el botón "Modo Kiosco", la interfaz entra en modo inmersivo a pantalla completa sin distracciones.
  • Auto-Foco Permanente: El cursor se ancla de forma persistente en el campo de lectura. Incluso si el operador hace clic accidentalmente fuera de la ventana, el foco se recupera automáticamente permitiendo disparar lecturas continuas sin tocar el ratón.
  • Salida de Emergencia: Se puede salir del modo kiosco en cualquier instante presionando la tecla Esc o pulsando el botón rojo superior "Salir de Kiosco".

9. Mantenimiento Preventivo, Auditoría y Pruebas de Estrés

  • Simulador de Carga y Pruebas de Estrés: Para certificar la capacidad de respuesta del servidor antes de la apertura de puertas, ejecute en la terminal del backend: 
    npm run test:stress
    Este test inyecta ráfagas masivas de registros concurrentes y acreditaciones QR simultáneas, reportando percentiles de latencia (p50, p95, p99), respuesta del rate-limiter y consumo de memoria del pool de conexiones PostgreSQL.
  • Despliegue Contenedorizado (Docker Compose): Para entornos de producción con Docker, se provee el archivo docker-compose.yml. Para levantarlo: 
    docker compose up -d
  • Revisión de Disco: Asegurar al menos 2 GB libres en la unidad para almacenamiento de logs y temporales de PDF.
  • Purga de Logs Transitorios: El planificador Cron ejecuta diariamente a las 03:00 AM la limpieza de registros de sesiones obsoletas.
  • Sincronización Git: Para aplicar actualizaciones del equipo de desarrollo, ejecutar: 
    bash scripts/git-sync.sh

11. Gestión de Temas y Perfiles Visuales del Backend

El personal de administración y soporte IT cuenta con herramientas centralizadas para configurar, respaldar y auditar los perfiles visuales del panel de control:

11.1 Selección del Perfil Institucional CABA

Para estaciones de trabajo oficiales, se recomienda aplicar como estándar la Paleta Oficial CABA Institucional. Esta paleta sincroniza los códigos cromáticos oficiales de la Ciudad (Azul Oscuro #1D3343, Amarillo GCABA #FFCD02 y Blanco #FCFCFC) con el resto de los sistemas de gobierno.

11.2 Procedimiento de Respaldo y Distribución de Paletas (JSON)

Para estandarizar el entorno visual en puestos de operadores o migrar personalizaciones entre navegadores:

  1. Acceder a Configuración ➔ 🎨 Temas del Backend ➔ Clic & Corrección en Vivo.
  2. Hacer clic en 📋 Exportar JSON: el sistema copiará al portapapeles la estructura con los 24 tokens normalizados de estilo.
  3. En la máquina de destino, abrir el panel, pulsar 📥 Importar JSON, pegar la definición y confirmar. El tema se activará de inmediato sin reiniciar servicios.

11.3 Estandarización Centralizada en Base de Datos (Default Global)

Para no depender de configuraciones puesto por puesto, el Superadministrador o Administrador puede almacenar el tema corporativo en el servidor central:

  1. Seleccionar o editar el tema deseado (por ejemplo, la Paleta Oficial CABA).
  2. Hacer clic en 💾 Fijar como Default Global (o Fijar tema activo como Default Global).
  3. Confirmar el diálogo. La configuración se persistirá en la tabla configuraciones_sistema de PostgreSQL bajo la clave 'tema_backend_default' y quedará registrada en los registros de auditoría (logs_auditoria).
  4. Todos los nuevos operadores o puestos que inicien sesión sin preferencias locales previas adoptarán automáticamente este diseño institucional.
🛡️
Resiliencia de Estilos: En caso de que un operador aplique una combinación de colores de bajo contraste que dificulte la lectura, basta con pulsar el botón ↺ Restablecer para retornar de inmediato a la plantilla base homologada.

12. Gestión de Temas y Perfiles Visuales del Frontend (Portal Público)

El portal público del congreso dispone de un sistema modular de tematización que permite a los operadores personalizar y estandarizar integralmente la experiencia visual para todos los visitantes, congresistas y expositores.

12.1 Las 4 Vistas Interactivas del Editor Clic & Corrección

El editor en Parámetros del Sistema ➔ 🌐 Temas del Frontend incluye un conmutador de 4 vistas interactivas que replican la totalidad de pantallas y páginas del portal:

  • 🏠 Vista 1: Home (Página Principal): Permite inspeccionar y ajustar la Barra de Navegación (Header), el bloque Hero principal con título y botón de llamado a la acción (CTA), el Banner de Notificaciones Push PWA, la sección informativa "Sobre el Congreso", las tarjetas de actividades y módulos formativos, los filtros interactivos del cronograma y el Pie de Página (Footer).
  • 📝 Vista 2: Inscripción y Login (/participa y /login): Permite ajustar la cabecera con indicadores de cupos y aforo, el contenedor del formulario oficial, cajas de texto (inputs), selectores desplegables de roles institucionales y el botón de confirmación de registro.
  • 🪪 Vista 3: Portal del Participante (/mi-credencial): Permite inspeccionar el pase digital oficial del congresista, incluyendo el fondo de la credencial, la cabecera institucional con escudo, el contenedor del código QR criptográfico HMAC, la insignia (badge) de rol o categoría de asistente y el botón de descarga del Certificado/Diploma A4 en PDF.
  • 📚 Vista 4: Centro de Recursos y FAQs (/materiales, /como-llego y FAQs): Permite ajustar las tarjetas de descargas de documentos/papers/flyers con sus etiquetas de tipo de archivo, y el acordeón interactivo de Preguntas Frecuentes (cajas contenedoras, color de pregunta y tipografía explicativa de respuesta).

12.2 Persistencia Centralizada en PostgreSQL (Default Global del Portal)

Al pulsar 💾 Fijar como Default Global en el editor del Frontend, la configuración activa se almacena en la tabla configuraciones_sistema bajo la clave 'tema_frontend_default'. Esto garantiza que cualquier ciudadano, asistente o evaluador que ingrese al portal desde cualquier dispositivo disfrute de la paleta oficial sin necesidad de configuraciones previas.

13. Journaling, Diagnóstico de Errores y Seguridad (Rate Limiting)

El sistema cuenta con un subsistema de telemetría y diagnóstico dinámico (Journaling) que permite registrar las transacciones HTTP, depurar incidentes en tiempo real e inspeccionar los payloads que provocan fallos, sin requerir reinicio de los servicios.

13.1 ¿Cómo Acceder al Módulo de Journaling?

El visor y conmutador de Journaling está restringido a operadores con rol de Administrador (Nivel 4 o 5):

  1. Ingresar al Panel de Administración con credenciales de Administrador.
  2. Hacer clic en el menú superior o lateral en ⚙️ Parámetros del Sistema (o navegar a la pestaña de configuración).
  3. En la barra de pestañas secundarias de configuración, seleccionar 📝 Journaling & Diagnóstico (ubicada junto a Variables Generales, Temas del Backend y Temas del Frontend).

13.2 Los 3 Niveles de Operación en Caliente

Desde el selector de nivel, el administrador puede conmutar el comportamiento del interceptor de tráfico de forma inmediata:

Nivel de Incidencia Tipo de Problema Acción de Contingencia / Contacto
Nivel 1 (Operativo) DNI no encontrado en padrón o acreditación manual Verificador en mesa de informes / Consulta en pestaña Acreditaciones.
Nivel 2 (Red y PWA) Caída de Wi-Fi en puerta de acceso Mantener PWA en modo offline. Los datos se sincronizan al volver la red.
Nivel 3 (Servicios) Puerto ocupado o servicio detenido Ejecutar Detener_Congreso.bat y luego Iniciar_Congreso.bat.
Nivel 4 (Crítico) Fallo de hardware o corrupción de datos Restaurar última copia desde backups/ con script de recuperación.
Nivel Estado Impacto en Rendimiento Casos de Uso
DISABLED APAGADO 0% Sobrecarga: Omite toda escritura a base de datos. Operación normal del congreso en días pico de alta concurrencia de acreditaciones.
ERRORS_ONLY SOLO FALLOS (Recomendado) Mínimo (< 0.1%): Solo guarda trazas HTTP 4xx y 5xx. Monitoreo proactivo de producción. Detecta errores sin saturar los discos con lecturas exitosas.
VERBOSE_ALL TRAZA COMPLETA Medio: Registra el 100% de las solicitudes entrantes y salientes. Pruebas de laboratorio, homologación de nuevas integraciones o detección de cuellos de botella de latencia.

13.3 Inspección Forense y Purga Automática

La vista interactiva permite:

  • Filtros por Nivel y Búsqueda: Filtrar eventos por niveles ERROR, WARN o INFO, además de filtrar por método HTTP (POST, GET, PUT) o ruta del endpoint.
  • Desplegable de Payloads: Al hacer clic en cualquier fila de evento, se expande un panel oscuro con el Cuerpo de la Petición (Request Body), los encabezados HTTP recibidos y la traza detallada del error (Stack Trace). Nota: Los campos sensibles como contraseñas son sanitizados automáticamente.
  • Métricas de Latencia: Permite ordenar los registros por duración en milisegundos (duracion_ms) para identificar consultas SQL lentas o demoras en la emisión de PDFs.
  • Botón 🗑️ Purgar > 7 días: Elimina con un solo clic los registros antiguos de la tabla logs_journaling para evitar el crecimiento innecesario del almacenamiento.

13.4 Limitación de Tasa (Rate Limiting de Seguridad)

Para proteger el backend contra ataques de fuerza bruta, denegación de servicio (DoS) o script scraping malicioso durante el congreso, se implementaron ventanas de limitación de solicitudes (express-rate-limit):

  • Ruta /api/registro (Inscripción pública): Máximo 25 peticiones cada 15 minutos por dirección IP de origen. Si un bot o usuario excede este cupo, recibe un código de error HTTP 429 Too Many Requests con el mensaje informativo correspondiente.
  • Ruta /api/credencial (Consulta y descarga de credenciales): Máximo 60 peticiones cada 5 minutos por dirección IP.
⚡
Manejo Operativo del Error 429: Si un puesto de acreditación en una red compartida (misma IP pública) reporta error 429 durante una prueba masiva, el personal de IT puede verificar el registro en el visor de Journaling o solicitar al operador esperar 5 minutos a que expire la ventana del limitador.

15. Operación de Envíos Masivos y Sandbox de Correo Servicio SMTP

Protocolos de contingencia y validación previa antes de despachar comunicaciones masivas a miles de inscriptos:

15.1 Activación del Modo Sandbox

En el archivo de entorno del backend (.env):

# Modo Sandbox: los correos no se envían al servidor SMTP sino que se registran en logs
EMAIL_SANDBOX=true

Con EMAIL_SANDBOX=true, los operadores pueden registrar asistentes de prueba, regenerar credenciales y probar la plantilla sin consumir cuota de envío diaria de Google Workspace ni saturar servidores institucionales.

15.2 Conmutación a Producción

Para habilitar el envío real durante el congreso:

EMAIL_SANDBOX=false
SMTP_HOST=smtp.gmail.com
SMTP_PORT=587
